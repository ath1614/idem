# idem.

**Two retries. One charge.**

A deterministic simulator of the same payment request arriving twice at the same time. Move the
jitter, change the strategy, and watch the window between reading an idempotency key and writing a
charge open and close.

Live: **https://idem.ath1614.workers.dev**

## Why

Idempotency is usually explained as "store the key". That is not the hard part. The hard part is
that a lookup and a write are two operations, and a second request can land between them. The
window is small, which is exactly why it survives code review and shows up as a customer dispute.

This lab makes the window visible.

## The model

Each attempt has two phases:

1. **read** at `readAt`, when the request looks up the idempotency key
2. **write** at `writeAt`, when the request inserts the charge

Phases are ordered by time, and the strategy decides what a write does when a charge already
exists:

| Strategy | Behaviour | Exactly once |
| --- | --- | --- |
| No key | every write charges | no |
| Read, then write | writes if the read saw no charge, even if another write landed since | no |
| Unique key | the unique index makes the loser fail, and it returns the winner | yes |
| Key and charge in one transaction | lookup, charge and key commit together | yes |

Every schedule is generated by `mulberry32` from a seed, so a result can be reproduced exactly.
`runBatch` replays the race across 200 seeds and reports how often a customer would be billed
twice.

## Run

```bash
npm install
npm test      # 10 tests, including 300-seed runs per strategy
npm run dev
npm run build
```

No analytics and no third-party scripts: the whole lab is a pure function behind a React view.

## Tests

- No-key bills all four attempts.
- Check-then-write duplicates when reads overlap.
- Unique key and atomic never duplicate across 300 seeded schedules.
- The schedule is deterministic for a seed and drifts for a different one.

## Limits

One database, no sharding. A unique index is exactly-once within a single writer; across shards
you need a request-level ledger and a routing key. The model is deliberately narrow so the race
stays legible.
